مركز المشروع: مكان واحد يعرف فيه الفريق وكل وكلاء الـ AI ما يحدث

أداة داخلية تعمل على شبكة المكتب. تجمع الخط الزمني للمشروع ومهام اليوم والقرارات والاحتياجات وإعادة التصميم والتوثيق. يقرأ منها Claude Code عند كل عضو ويكتب فيها عبر MCP، فتنتقل التحديثات وحدها بدل أن يشرحها كل عضو للآخرين شفهيًا.

الخلاصة

المشكلة، والحل في جملة، وما تقرّر حتى الآن

المشكلة

كل عضو يعمل مع الـ AI في جلسة خاصة به، وما تعرفه الجلسة يضيع عند انتهائها. التحديثات تنتقل شفهيًا، والتوثيق الموجود غني لكنه للقراءة فقط: لا يستطيع أحد أن يوافق منه أو يطلب أو يحجز مهمة. والقرارات والاحتياجات (مثل توكنات مزودي الدفع) لا يتابعها أحد بوضوح.

الحل

كل شيء يصبح بطاقة لها نوع ومالك وحالة. الخط الزمني يعرض البطاقات بالترتيب. البطاقات تُلتقط تلقائيًا من Git وعقد الـ API وجلسات Claude Code والمختبر، وتُوجَّه القرارات إلى الشخص الذي يملك حق اتخاذها. والـ AI يدخل إلى كل ذلك عبر MCP.

الفكرة الأساسية: البطاقة الموحّدة

سبعة أنواع، وكلها لها نفس الحقول الأساسية. لذلك يعرضها الخط الزمني والبحث والـ MCP بطريقة واحدة

مهمة

Task

عمل له تخصص (باك أو فرونت أو تصميم أو QA)، وأولوية من P0 إلى P3، وحجم من S إلى XL، وبرومبت جاهز، ومعايير قبول، ومن حجزها، والفرع الذي تعمل عليه.

قرار

Decision

سؤال وخيارات، لكل خيار مميزاته وعيوبه. له دور مخوَّل بالقرار، وموعد نهائي، وقائمة بما يتوقف عليه. بعد القرار يُكتب ADR في Git.

احتياج

Need

شيء مطلوب من شخص: توكن، أو حساب، أو قيمة للتحقق، أو ملف. تتابع الأداة حالته فقط: مطلوب، ثم قيد التنفيذ، ثم سُلِّم إلى الخزنة، ثم تم التحقق منه.

تغيير

Change

Commit أو PR أو تغيير في عقد الـ API أو ملخص جلسة AI. يُنشأ تلقائيًا ولا يكتبه أحد بيده.

إعادة تصميم

Redesign

نسخة من المختبر لها لقطات وتقرير ux-critic وحالة. تُعرض للموافقة، ثم تتحول إلى مهمة نقل (port) للمشروع.

وثيقة

Doc

مرآة لملف في Git. نصها لا يُحرَّر داخل الأداة، لكنها تُربط بالبطاقات ويُعلَّق عليها.

إصدار

Release

مجموعة تغييرات تذهب إلى الإنتاج، ومعها ملاحظات تُولَّد بالـ AI لكل جمهور: الفريق والمالك والمحاسب.

الحقول المشتركة

Card {
  id, workspace, type, title, body (rich text),
  status, priority, owner_role, assignee, created_by (human | agent:<user>),
  links: [card | doc | commit | pr | url],   // "blocks / blocked-by / relates-to"
  source: manual | git | openapi | claude-session | redesign | import,
  due_at, decided_at, tags, watchers, comments, history (append-only)
}

القاعدة الأهم: لا تُحذف أي بطاقة، ولا يُعاد كتابة تاريخها. كل تغيير حالة يصبح حدثًا في الخط الزمني. بهذا يكون الخط الزمني سجلًا كاملًا موثوقًا.

الصفحات

واجهة عربية أولًا (RTL) مع الإنجليزية، وبوضع فاتح وليلي، وبنفس مكوّنات لوحة التحكم (shadcn + Tailwind v4)

يومي

أول ما يراه العضو: الملخص الصباحي، وما ينتظره مني (قرارات واحتياجات ومراجعات)، ومهام تخصصي الجاهزة للحجز، وما تغيّر منذ آخر دخول.

الخط الزمني

كل البطاقات بالترتيب، مع تصفية حسب الدور والنوع والمستودع والموديول والفترة. وعرض «ما الذي حدث هذا الأسبوع» بفقرة يكتبها الـ AI.

المهام

لوحة Kanban وقائمة. زر «احجز» وزر «انسخ البرومبت»، ورابط يفتح المهمة في Claude Code. والتصفية حسب التخصص.

غرفة القرارات

القرارات المفتوحة مرتبة حسب الموعد النهائي، ولكل قرار ما يتوقف عليه. صاحب القرار يختار ويكتب سببه، ثم يُفتح ADR تلقائيًا.

الاحتياجات

لوحة لما ينقصنا من الخارج: توكنات، حسابات، عقود، قيم يتحقق منها المحاسب. لكل احتياج مسؤول وموعد وما يتوقف عليه.

التسليمات

ما سلّمه فريق لآخر: تغيّر في العقد، أو endpoint جديد، أو تصميم معتمَد. يظهر ما لم يُستلم بعد، وكم مضى عليه.

إعادة التصميم

معرض نسخ المختبر جنبًا إلى جنب مع لقطات وتقرير المراجعة، وأزرار موافقة أو رفض أو طلب تعديل.

المعرفة

بوابة للوثائق: البزنس والمعمارية والـ API والـ ADR وخريطة المنصة، مع بحث واحد في كل شيء.

اسأل المشروع والعضو الجديد

خانة سؤال تجيب من الوثائق والبطاقات مع ذكر المصدر. ومسار تعريف تفاعلي بالبزنس والمشروع حسب التخصص.

    دورة حياة القرار

    1. يُفتح القراريفتحه إنسان أو وكيل AI عندما يحتاج اختيارًا لا يملكه، عبر الأداة request_decision. يحدد الخيارات ومن يقرّر والموعد وما يتوقف عليه.
    2. التنبيهيصل إلى صاحب الدور داخل الأداة وعبر إشعار المتصفح وTelegram، وبالبريد إن لم يتفاعل.
    3. النقاشتعليقات على البطاقة، ويمكن طلب رأي من الـ AI يقارن الخيارات من الوثائق.
    4. القرارصاحب الدور يختار ويكتب السبب في سطر واحد. البطاقات المتوقفة تتحرر وتُبلَّغ.
    5. التوثيقتكتب الأداة ADR بالصيغة المعتمدة وتفتح به PR في المستودع المناسب، ويظهر القرار لكل وكيل AI في المرة القادمة.
    الموعد النهائي له أثر حقيقي: قبله بيوم يصل تذكير، وعند تجاوزه يُصعَّد القرار إلى مدير المشروع. هكذا لا يبقى قرار معلقًا بلا نهاية.

    الالتقاط التلقائي: التحديثات تكتب نفسها

    أربعة مصادر اخترتها، وكلها تعمل والأداة على شبكة المكتب دون أن يصل إليها أي اتصال من الخارج

    1 · ملخص جلسات Claude Code

    طبقتان. الأولى: قاعدة في CLAUDE.md تجعل الوكيل يستدعي log_session عند إنهاء أي مهمة، فيرسل ما تغيّر وما بقي وما يحتاجه الفريق الآخر. الثانية احتياطية: hook من نوع SessionEnd يرسل حقائق Git للجلسة (الفرع والـ commits والملفات). إذا لم يصل ملخص يكتبه الـ AI، تولّده الأداة من الـ diff.

    2 · Commits وPRs من GitHub

    لا يمكن لـ webhook من GitHub أن يصل إلى جهاز داخل الشبكة، لذلك يسأل عامل (worker) في الأداة GitHub كل 2 إلى 5 دقائق عن المستودعات الثلاثة. يحتاج توكنًا بصلاحية قراءة على الحسابين mohmedofficial515 وAlremaal-Co. الـ commits المتتالية في نفس الفرع تُجمع في بطاقة واحدة.

    3 · تغيّرات عقد OpenAPI

    عندما يتغير openapi/openapi.json في الباك إند، يشغّل العامل oasdiff بين النسختين ويصنّف التغيير: كاسر أم غير كاسر. ثم يُنشئ بطاقة تسليم لفريق الفرونت فيها قائمة التغييرات وبرومبت «شغّل pnpm api:sync وأصلح الأنواع». هذا يلغي الحاجة إلى contract-changes.md اليدوي (ويُستورد السجل القديم كتاريخ).

    4 · نسخ مختبر redesign

    تراقب الأداة ملفات README.md في نسخ المختبر وتقرأ الحالة من الـ front-matter. أي نسخة جديدة أو تغيّر في الحالة يصبح بطاقة. وموافقة المالك من الأداة تكتب الحالة approved في الملف وتُنشئ مهمة نقل للـ redesign-porter.

    ملاحظة: مجلد F:\Goteav\redesign ليس مستودع Git الآن. إذا كانت الأداة على نفس جهاز المالك فستقرأه مباشرة. وإلا نحتاج رفعه إلى مستودع (انظر الأسئلة المفتوحة).

    أدوات الـ MCP المقترحة

    الأداةما تفعلهمتى يستخدمها الوكيل
    get_project_briefملخص البزنس والمعمارية والقرارات الثابتة لهذا الدوربداية كل جلسة
    whats_newما تغيّر منذ آخر جلسة لي: تسليمات وقرارات وتغييراتبداية كل جلسة
    search_docs / get_docبحث في الوثائق والـ ADR والبطاقات مع روابط المصدرعند الحاجة لمعلومة
    list_tasks / claim_task / update_taskجلب مهام تخصصي، وحجز مهمة، وتحديث حالتها وفرعها وملاحظاتها«ما مهمتي التالية؟»
    log_sessionكتابة ملخص الجلسة: ما تغيّر وما بقي وتسليمات للفريق الآخرنهاية كل مهمة (إلزامي بقاعدة)
    request_decisionفتح قرار بخيارات وموعد وما يتوقف عليهعندما يواجه الوكيل اختيارًا لا يملكه
    create_needتسجيل احتياج (توكن أو قيمة أو حساب) بلا أي قيمة سريةعندما يتوقف العمل على شيء من الخارج
    create_handoff / list_handoffsتسليم عمل لفريق آخر، أو استلام ما سُلِّم ليبعد تغيير يؤثر على الفريق الآخر
    get_decisionقراءة قرار ونتيجته وسببهقبل تنفيذ شيء يرتبط بقرار

    إلى جانب الأدوات، يعرض الـ MCP برومبتات جاهزة مثل /hub:start (ابدأ يومك: الجديد ومهامي) و/hub:next (احجز المهمة التالية في تخصصي وابدأ) و/hub:done (أنهِ المهمة واكتب الملخص والتسليمات).

    مقطع CLAUDE.md الذي تضيفه حزمة الفريق 
    # Project Hub
- At session start call hub.whats_new and read decisions that affect your task.
- Never assume a business rule: hub.search_docs first, then hub.request_decision if still unclear.
- When something blocks you from outside (token, account, value), call hub.create_need — never paste secrets.
- When your change affects another team (API contract, shared component), call hub.create_handoff.
- Before you finish, call hub.log_session with: changed, remaining, handoffs, follow-up tasks.

    كيف يمر يوم العمل بعد الإطلاق

    مثال واقعي من وضعكم الحالي: توكن مزود دفع وتغيير في العقد

    1. 08:30: الملخص الصباحيكل عضو يفتح «يومي». مطوّر الفرونت يقرأ: «أمس غيّر الباك إند عقد الاسترداد (تغيير كاسر). هناك تسليم ينتظرك، و3 مهام في تخصصك جاهزة للحجز».
    2. 08:40: حجز المهمةيكتب في Claude Code: /hub:next. الوكيل يحجز مهمة مزامنة العقد، ويقرأ التسليم والـ diff والوثيقة المرتبطة، ثم يبدأ على الفرع الصحيح.
    3. 10:15: احتياجوكيل الباك إند يصل إلى ربط Moyasar فيجد أن التوكن الحي غير موجود. يستدعي create_need: «توكن Moyasar الحي — المسؤول: المالك — يتوقف عليه: مهمة تفعيل الدفع». يصل التنبيه إلى المالك على Telegram.
    4. 11:00: قرارالوكيل يجد أن رسوم Moyasar تُحسب إما على العميل أو على المنصة. يفتح request_decision موجّهًا إلى المحاسب وموعده غدًا. يكمل في جزء آخر من المهمة بدل أن يخمّن.

    المشاريع مفتوحة المصدر: هل نعتمد على شيء جاهز؟

    النتيجة: لا يوجد مشروع يغطي الفكرة كاملة، لكن مكتبات جاهزة كثيرة توفّر معظم العمل

    منصات كاملة درسناها

    المشروعالترخيصما يغطيهما ينقصه لناالحكم
    PlaneAGPL-3.0مهام، ودورات (cycles)، وموديولات، وصفحات، وMCP رسمي (makeplane/plane-mcp-server)لا يوجد فيه خط زمني موحّد، ولا قرارات لها صاحب قرار وموعد، ولا احتياجات، ولا التقاط من جلسات AI. وبعض الـ APIs غير متاحة في نسخة Communityنستلهم منه نموذج الدورات وصندوق الطلبات (intake) فقط
    HulyEPL-2.0مهام ووثائق ودردشة في منصة واحدةثقيل جدًا: من 8 إلى 16GB RAM، مع MongoDB وElastic وCockroachDB. وتخصيصه صعبغير مناسب
    OpenProjectGPL-3.0إدارة مشاريع كلاسيكية (Gantt وwork packages)مبني على Rails، وثقيل، ولا يرتبط بالـ AIغير مناسب
    Outline / DocmostBSL 1.1 / AGPL-3.0ويكي للتوثيققررنا أن الوثائق تبقى في Git، فلا نحتاج ويكي منفصلًاغير لازم
    BackstageApache-2.0بوابة للمطورين: كتالوج وTechDocsمصمَّم لشركات كبيرة، وإعداده وصيانته ثقيلان على فريق صغيرنستلهم منه فكرة الكتالوج
    GitHub Projects + Issuesخدمةمهام مرتبطة بالكود، وMCP رسميالأدوار والقرارات والعربية والخط الزمني كلها ضعيفةنستخدمه مصدرًا فقط

    المكتبات التي سنبني عليها

    @modelcontextprotocol/sdk

    الـ SDK الرسمي لكتابة MCP server بـ TypeScript، ويدعم Streamable HTTP.

    Claude Code hooks + skills

    SessionEnd للتسجيل الاحتياطي، وskill للبرومبتات الجاهزة. موجودة في Claude Code نفسه.

    oasdiff

    يقارن نسختين من OpenAPI ويكتشف التغييرات الكاسرة. له CLI وGitHub Action رسمي.

    Octokit

    للتعامل مع GitHub API: سحب الـ commits والـ PRs، وفتح PR للـ ADR.

    pgvector

    بحث دلالي داخل Postgres نفسه. لا نحتاج قاعدة بيانات متجهات منفصلة.

    BlockNote / Tiptap

    محرّر نص غني بنمط Notion لنص البطاقات والتعليقات.

    grammY + web-push

    بوت Telegram بأزرار موافقة، وإشعارات المتصفح عبر VAPID.

    gray-matter + chokidar

    لقراءة front-matter نسخ المختبر ومراقبة تغيّر الملفات.

    Infisical (اختياري)

    خزنة أسرار مفتوحة المصدر تُستضاف ذاتيًا. فيها تُحفظ قيم «الاحتياجات»، والأداة لا تخزنها أبدًا.

    ومن داخل مشروعكم نعيد استخدام: مولّد docs/map (يتحول إلى عرض داخل الأداة)، و_suggestions.yaml و_decisions.yaml (بيانات أولية)، والأنماط المعمارية للباك إند (DDD وCQRS وZod)، ومهارة graphify عند الحاجة لخريطة الكود.

    الأمان

    أداة داخلية، لكنها ترى كل شيء عن المشروع، لذلك قواعدها صارمة من البداية

    • لا أسرار في الأداة أبدًا. الاحتياج يخزن الحالة واسم المكان في الخزنة فقط. وفلتر على كل نص وارد (بما فيه ملخصات الـ AI) يكتشف ما يشبه المفاتيح ويخفيه ويحذّر صاحبه.
    • توكن MCP شخصي لكل عضو. له نفس صلاحيات دوره، ويُلغى من صفحة الحساب، ويُسجَّل كل استدعاء له. الوكيل لا يتخذ قرارًا ليس من حق صاحبه.
    • القرارات المالية والإدارية للبشر فقط. الوكيل يستطيع أن يفتح قرارًا، لكن لا يستطيع أن يغلقه.
    • الشبكة: الأداة لا تقبل إلا اتصالات من شبكة المكتب (قاعدة في جدار حماية Windows لـ Private network فقط)، وPostgres وRedis لا يُكشفان خارج Docker.
    • سجل تدقيق لا يُمحى: كل تغيير يحفظ من فعله، وبأي وسيلة (الواجهة أو الـ MCP أو تلقائيًا)، ومتى.
    • نسخ احتياطي: pg_dump يومي إلى قرص آخر. والوثائق محفوظة أصلًا في Git.

    التعميم: نفس الأداة لأي مشروع لاحقًا

    لأنك قلت إن المبدأ إذا نجح سيُطبَّق على مشاريع أخرى، فالتصميم متعدد المشاريع من اليوم الأول

    مساحة عمل لكل مشروع

    Goteav مساحة. ومشروع جديد مثل Bitaqaty مساحة أخرى، لها مستودعاتها وأدوارها ووثائقها، والبيانات معزولة بين المساحات.

    قوالب

    قالب أدوار (فريق ويب أو فريق موبايل)، وقالب أنواع قرارات، وقالب مصادر التقاط. مشروع جديد يبدأ في دقائق.

    محوّلات (adapters)

    كل مصدر التقاط (GitHub، OpenAPI، مجلد تصميم، GitLab لاحقًا) محوّل منفصل له نفس الواجهة. إضافة مصدر جديد لا تمس الباقي.

    مراحل التنفيذ المقترحة

    تقدير أولي لكل مرحلة، يُراجَع في مرحلة التخطيط. وكل مرحلة قابلة للاستخدام فعلًا عند انتهائها

    H0~1 أسبوع

    الأساس

    مستودع الأداة، وDocker Compose، والحسابات والأدوار، ونموذج البطاقة، والخط الزمني، واستيراد القرارات والاقتراحات وتقارير الحالة الموجودة. بعدها: يرى الفريق تاريخ المشروع كله في مكان واحد.

    H1~1 أسبوع

    MCP وClaude Code

    الـ MCP server، والتوكنات الشخصية، وحزمة الفريق (skill وhook ومقطع CLAUDE.md)، وlog_session وwhats_new. بعدها: تنتهي التحديثات الشفهية.

    H2~1 أسبوع

    الالتقاط التلقائي

    polling لـ GitHub، وتسليمات العقد بـ oasdiff، ومراقبة المختبر. بعدها: لا يحتاج أحد أن يكتب contract-changes.md بيده.

    H3~1 أسبوع

    القرارات والاحتياجات والتنبيهات

    غرفة القرارات بمواعيد وتصعيد، ولوحة الاحتياجات، وإشعارات المتصفح وTelegram والبريد، وفتح PR تلقائي للـ ADR. بعدها: لا يبقى قرار أو توكن معلقًا دون متابعة.

    H4~1 أسبوع

    يومي والمهام والملخص الصباحي

    صفحة «يومي»، ولوحة المهام بالحجز، وزر «نفّذ بالـ AI»، والملخص الصباحي لكل دور.

    H51–2 أسبوع

    المعرفة والعضو الجديد

    بوابة الوثائق، والبحث الدلالي، وخانة «اسأل المشروع» مع ذكر المصادر، ومسار التعريف حسب التخصص.

    H6لاحقًا

    التعميم والسحابة

    تعدد المساحات والقوالب، ثم الانتقال إلى VPS إذا احتجتم، مع تجربة الأداة على مشروع ثانٍ.

    الطريقة: نفس أسلوبكم، أي وثيقة تصميم توافق عليها أولًا، ثم كل مرحلة بفرع واختبارات. ويمكن أن تعمل الأداة نفسها مساحةَ عمل أولى لمشروعها، فنتابع بناءها من داخلها بدءًا من H1.

    أسئلة مفتوحة قبل مرحلة التخطيط

    لا تمنع الفكرة، لكن نحتاج إجاباتها قبل كتابة وثيقة التصميم

    1
    أي جهاز يستضيف الأداة؟ جهاز المالك أسهل (يرى مجلد redesign مباشرة) لكنه يجب أن يبقى مفتوحًا. وجهاز صغير مخصص أكثر ثباتًا.
    2
    مجلد redesign: هل نرفعه إلى مستودع Git حتى تقرأه الأداة من أي جهاز، أم تبقى الأداة على نفس جهازه؟
    3
    مفتاح Claude API للأداة: الملخصات و«اسأل المشروع» تحتاج مفتاحًا وميزانية شهرية. ما الحد المقبول؟ أو نؤجلها ونعتمد على Claude Code وحده في البداية؟
    4
    البحث الدلالي بالعربية: نماذج embeddings عبر خدمة (مثل Voyage)، أم نموذج محلي (مثل bge-m3 عبر Ollama) مجاني لكنه يحتاج موارد من الجهاز؟
    5
    الفريق: كم عضوًا، وما أدوار كل منهم بالضبط؟ وهل المحاسب ومدير المشروع شخصان مختلفان؟
    6

    7
